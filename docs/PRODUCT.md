# Product direction

Status: current product intent for post-v1 development.

## Vision

`mojit` is evolving from a single-purpose animated Unicode-text CLI into a
**lightweight terminal-native visual scene and ambience engine**, with Japanese
typography as a central capability and an anime/Japanese visual identity expressed
through scenes and presets rather than hard-coded into the architecture.

The end result should still feel like a small command-line program, not a desktop
application framework.

## Current baseline

Version 1 established a strong technical base:

- full-screen pixel-based rendering inside WezTerm;
- correct horizontal and vertical CJK typography;
- deterministic effects and compositing;
- resize-aware fixed-step animation;
- bounded runtime state and terminal restoration;
- reproducible Windows x64 packaging.

`SPEC.md` describes that implemented v1 contract. Phases 0-6 and their ADRs are
historical evidence, not the roadmap for future product work.

Passing the old v1 gates does **not** mean the desired product is finished. The next
work is about turning that renderer into a useful scene-composition model and making
the visual result substantially richer while preserving the reliable core.

## Target experience

The simple v1 use case must remain natural:

```powershell
mojit "電脳世界"
```

In addition, `mojit` should eventually be able to run named or configured ambient
scenes composed from independent visual layers. Exact CLI syntax is not frozen yet;
the following is illustrative:

```powershell
mojit --scene rainy-night
```

A scene may combine, for example:

- large horizontal or vertical Japanese text;
- existing text effects such as neon/glitch/chromatic/pulse;
- procedural rain, snow, stars, drifting particles, or similar ambience;
- backgrounds and overlays generated by the rendering core;
- later, optional richer image-capable layers when an appropriate terminal backend
  is deliberately introduced.

The intended result is a program that can be left running indefinitely as an
animated terminal composition, reacts correctly to resize, remains visually stable,
and exits cleanly with `Ctrl+C`.

## Product principles

Priority order for post-v1 work:

1. convincing visual result in real interactive use;
2. reliable indefinite execution and clean terminal lifecycle;
3. composability of scenes and layers;
4. deterministic/testable rendering core;
5. simple configuration and discoverable presets;
6. low operational and architectural complexity;
7. performance sufficient for smooth ambient use;
8. future backend extensibility only when demanded by an actual second backend.

The project should prefer a small number of strong primitives over many special-case
effects.

## Core capabilities we want

### 1. Backward-compatible simple text mode

Existing v1 commands remain useful. A user should not have to understand scenes or
layers to display one animated text composition.

### 2. Scene composition

A scene is conceptually an ordered composition of independent layers that ultimately
produces one frame. The architecture should allow multiple visual elements to coexist
without each element knowing about terminal transport or global orchestration.

The exact Python types and APIs are not frozen by this document.

### 3. Japanese typography remains first-class

Correct CJK rendering is not merely a legacy feature. Horizontal and vertical
Japanese text should remain one of the main visual building blocks of the product.

### 4. Procedural ambience

The near-term visual vocabulary should expand beyond transformations of a single text
mask. We want reusable procedural layers such as rain, stars, snow, drifting
particles, and similar effects that can be composed with text.

### 5. Data-driven scenes and presets

Once the scene model is stable, users should be able to select built-in presets and
define scenes through configuration without writing Python code.

Configuration should describe product concepts, not expose incidental internal class
structure.

### 6. Terminal backend remains a boundary

Windows 11 + WezTerm is the primary supported environment during the current
roadmap. The rendering/application core must not become coupled to WezTerm.

A native Kitty-terminal backend is a plausible future direction **after** the core
scene functionality is mature. It is intentionally not current work. Existing
WezTerm transport may use the Kitty Graphics Protocol; that protocol detail must not
be confused with supporting the Kitty terminal application itself.

## Near-term non-goals

Do not pursue these while the current scene-engine roadmap is incomplete:

- native Kitty-terminal support;
- cross-terminal abstraction for terminals we do not actually support yet;
- GUI/TUI scene editor;
- plugin ecosystem or scripting language;
- OpenGL/Vulkan/DirectX renderer;
- audio playback or media-player features;
- network services, accounts, synchronization, or cloud state;
- Live2D/3D character engine;
- arbitrary image/video playback;
- a rewrite of the proven v1 typography, lifecycle, packaging, or transport layers
  without a concrete defect or roadmap requirement.

## Success criterion

The post-v1 direction is successful when `mojit` can produce several visually
distinct, polished ambient scenes from reusable layers while:

- preserving the simple v1 text workflow;
- remaining deterministic and testable below the imperative shell;
- running for long periods with bounded state;
- handling terminal resize correctly;
- restoring terminal state reliably;
- keeping Windows + WezTerm as a well-supported primary path;
- leaving room for a future Kitty backend without building that backend prematurely.
